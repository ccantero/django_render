# Render/Django security audit

Audit date: 2026-10-31. Report path requested as `AUDIT_2026-11.md`.
Scope: this repository and the public Render/Django site only.
This phase records findings. It does not change application behavior, rotate keys, or deploy.

No critical finding was proven. Two high findings are proven. Several items remain `NEEDS_RUNTIME_VERIFICATION` and are marked that way below.

Sanitization: this report contains no secret values, no IP addresses, and no connection strings. Scanner output was reduced to detector name, file, commit, and verification state before it was written here.

## VPS

Owned by another planner. To be filled later. This audit does not inspect the VPS, host firewall, or bot process.

## Planner baseline and this re-check

Planner baseline, measured 2026-10-31 and supplied with the audit request:

- Sensitive file paths return 404 with the generic page and no DEBUG trace.
- `/admin/` returns 302 to `/admin/login/` (default URL).
- HSTS with preload, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, and `Referrer-Policy: same-origin` are present.
- Cloudflare is in front.
- `x-render-origin-server` shows gunicorn.

This audit repeated unauthenticated GET and a sample of HEAD requests against `https://www.cantero-solutions.com.ar` on 2026-10-31. Those results match the baseline. The re-check is runtime evidence for that hostname, not `NEEDS_RUNTIME_VERIFICATION`.

The Render `*.onrender.com` hostname is not named in this repository. `ALLOWED_HOSTS` uses `www.cantero-solutions.com.ar` when `RENDER` is set, and appends `RENDER_EXTERNAL_HOSTNAME` only when the platform provides it. That hostname was not guessed. Checks against it are `NEEDS_RUNTIME_VERIFICATION`.

### R-06 — default admin URL

Severity: low.

Evidence: GET and HEAD `/admin/` returned 302 with `location: /admin/login/?next=/admin/`. GET `/admin/login/` returned 200, 4268 bytes, marker hits none. No DEBUG trace.

This matches the planner baseline. The login form is the default Django admin path.

Proposed fix: serve admin on a non-default path and keep staff authentication. Do that in a later change; this audit does not rename it.

### R-03 — public API schema and docs

Severity: medium.

Evidence: `django_render/urls.py` mounts `SpectacularAPIView` at `api/schema` and `SpectacularSwaggerView` at `api/docs` without an extra permission class. GET and HEAD `/api/schema` returned 200, content type `application/vnd.oai.openapi`, GET size 16665 bytes, marker hits none. GET `/api/docs` returned 200, 4639 bytes, HTML, marker hits none.

The schema named these paths and no others in the parsed path list: `/api/bot/health`, `/api/bot/inventory/ETHUSDT`, `/api/login/`, `/api/profiles/`, `/api/profiles/{id}/`, `/api/schema`, `/currencyconverter/json/currencies/`, `/currencyconverter/json/currencies/{key}/`, `/currencyconverter/json/exchangerates/`, `/currencyconverter/json/exchangerates/{key}/`.

GET `/api/login/` returned 405 and 40 bytes, marker hits none. No login POST was sent.

Proposed fix: require an authenticated operator for `/api/schema` and `/api/docs`.

### R-01 — public profile list

Severity: high.

Evidence: `profile.views.UserProfileViewSet` sets `permission_classes` to `profile.permissions.UpdateOwnProfile`. That class implements `has_object_permission` only. DRF's base `has_permission` allows the request, and a list action does not call object permissions. The serializer fields are `id`, `email`, `name`, and write-only `password`.

GET `/api/profiles/` returned 200, 108 bytes, `content-type: application/json`. The JSON shape was a paginated list with count 1 and one result object. Result keys were `email`, `id`, and `name`. The `password` key was absent. Values were not copied into this report.

`manage.py check --deploy` also reported that the diagnostics views are omitted from the schema guess (`drf_spectacular.W001` and `W002`). That warning is separate from this exposure: the schema document itself is still public (R-03).

Proposed fix: deny anonymous and non-owner reads, and do not return `email` to other callers. The create and update methods were not called. Whether an unauthenticated write succeeds is `NEEDS_RUNTIME_VERIFICATION`; the code path does not apply the object check on create.

### R-08 — no Content-Security-Policy

Severity: low.

Tool versions: gitleaks 8.28.0, trufflehog 3.88.35. Both scanned the full git history available in this clone (gitleaks reported 164 commits). They were installed in the audit environment only. They are not project dependencies.

- `django_render/.env` is not in HEAD. It was added in `fce611d4594b6a8780a776f158b5a71255a917d0` (2022-11-12, initial commit) and deleted in `33206444b78f78329c480b4aa5d650ced07e4fb7` (2022-12-01). The blob remains reachable from history.

- The gitignore rules for those env paths were introduced in `ffe7268824e0083149a93356125a0921cc95a016` (2026-04-29), after the file had already been deleted. Ignore rules do not remove the historical blob.

- trufflehog reported 2 unverified results and 0 verified results.

  - Detector `Github`, verified false, file `.codex/workflow-evidence.md`, commit `9aff094e5a073d24893e38d67f60150694adb0f6`, line 9. The matched text is a 40-character hex git SHA that exists in this repository. It is scanner noise, not a credential.

### R-02 — historical database URL in git

Severity: high.

Evidence: the history commands and the trufflehog Postgres result above. Gitleaks did not flag the same blob; trufflehog did. Absence from HEAD is not absence from history.

Whether that 2022 credential still authenticates is `NEEDS_RUNTIME_VERIFICATION`. This audit did not try it again.

Proposed fix: treat the historical URL as leaked. Rotate the database credential if it was ever a real password, confirm the current deployment URL is a different credential, and decide separately whether to rewrite published history. Rotation and history rewrite are out of scope for this phase.

### R-09 — historical settings bytecode

Severity: low.

Evidence: `django_render/__pycache__/settings.cpython-38.pyc` was in the initial tree and is absent from HEAD. Two commits touch the path. The bytecode contains the setting names `SECRET_KEY`, `ALLOWED_HOSTS`, `DATABASES`, and `AUTH_PASSWORD_VALIDATORS`. It does not contain the byte strings `DATABASE_URL`, `postgres`, `sqlite`, `TUTORIAL_BOT_TOKEN`, or `TELEGRAM`. No value was copied.

Proposed fix: keep bytecode out of git. No current tree cleanup is required.

### Logs and error responses

Code review of the four named secrets, current tree:

- `SECRET_KEY` is read in settings and used as an HMAC key in `profile/passkeys.py`. No logger call prints it.
- `TUTORIAL_BOT_TOKEN` is interpolated into the outbound Telegram URL in `core/views.py`. Delivery failures log `telegram_http_status`, `exception_class`, `telegram_error_code`, and `telegram_description`. They do not log the request URL. `requests` exceptions are caught inside `_deliver_telegram` before the photo fallback's `exc_info=True` handler.
- `TELEGRAM_WEBHOOK_TOKEN` is compared in `listener`. The rejection log line is `Telegram webhook rejected invalid secret token` with `stage=secret_validation`. The token is not an argument.
- `BOT_DIAGNOSTICS_API_TOKEN` is compared with `hmac.compare_digest` in `DiagnosticsBearerAuthentication`. Failures raise `AuthenticationFailed` with the fixed text `Invalid diagnostics credentials.`

Anonymous production responses checked above (404, 403, 401, and the admin login page) had no DEBUG markers. Production log files were not available. Whether a live worker log contains a token is `NEEDS_RUNTIME_VERIFICATION`.

### ALLOWED_HOSTS

From `django_render/settings.py`: the list starts as `www.cantero-solutions.com.ar`. If `RENDER` is absent, the list is replaced with `127.0.0.1`. If `RENDER_EXTERNAL_HOSTNAME` is set, that value is appended. There is no wildcard. The public-site responses show that production accepted the public hostname. The platform hostname itself is `NEEDS_RUNTIME_VERIFICATION` (see the baseline section).

### R-05 — proxy TLS header trust

Severity: medium.

Evidence: when `CC_DEBUG` is false, settings set `SECURE_PROXY_SSL_HEADER` to `HTTP_X_FORWARDED_PROTO` / `https`, plus HSTS, SSL redirect, and secure session and CSRF cookies. The code comment says to trust the header only when the proxy overwrites a client-supplied value and clients cannot reach the app server directly. The public hostname presents Cloudflare in front and `x-render-origin-server: gunicorn`. This audit did not send a forged `X-Forwarded-Proto` and did not request the platform hostname.

Proposed fix: confirm the edge overwrites `X-Forwarded-Proto` and that the origin port is not reachable except through that edge. Record the platform hostname from the deployment console rather than guessing it. This phase does not change the setting.

### R-04 — Telegram webhook allowlists

Severity: medium.

Evidence from `core/views.py` and `core/telegram_diagnostics.py`:

- `listener` rejects a request unless the `X-Telegram-Bot-Api-Secret-Token` header equals `TELEGRAM_WEBHOOK_TOKEN`. Unauthenticated GET `/telegramapi/listener/` returned 403 (see above). The header value was not tested.
- Diagnostics commands and `/help` call an allowlist check. An empty `TELEGRAM_ALLOWED_CHAT_IDS` or `TELEGRAM_ALLOWED_USER_IDS` contributes no ids. If both are empty, no chat id and no user id can match, so the check returns false and the reply is the unauthorized diagnostics text. A non-empty list on either side can authorize. One empty list does not by itself authorize everyone.
- `/start`, `/getmyinvest`, and the fallback reply do not call the allowlist. `_record_telegram_message` runs before the allowlist check, so a text update is persisted before authorization when the database write succeeds.
- The webhook secret authenticates Telegram as the sender of the HTTP request. It does not identify an operator. Any person who can message the bot causes Telegram to present that secret.

Production allowlist values were not read. Whether production sets either allowlist is `NEEDS_RUNTIME_VERIFICATION`. The empty-allowlist behavior above is what the code does.

`docs/DATA_CONTRACT.md` requires diagnostics to stay on the configured allowlists and to avoid raw exceptions, database URLs, tokens, and environment values. The diagnostics branch matches that rule. The gap is the non-diagnostic branch and the write that happens first.

Proposed fix: authorize with the allowlist before persistence and before any reply. Keep both-empty as fail closed. This phase does not change the view.

### R-07 — webhook compare is not constant-time

Severity: low.

Evidence: `listener` uses `token != TELEGRAM_WEBHOOK_TOKEN`. `DiagnosticsBearerAuthentication` uses `hmac.compare_digest` and rejects a configured value shorter than 32 characters.

Proposed fix: compare the webhook header with `hmac.compare_digest` in a later change.

### Diagnostics API token

`BOT_DIAGNOSTICS_API_TOKEN` defaults to empty. `DiagnosticsBearerAuthentication` rejects a missing, malformed, or short expected value and uses `hmac.compare_digest` when a bearer token is present. `IsAuthenticated` then denies anonymous requests. Empty therefore disables the API. Production GET `/api/bot/health` without a bearer token returned 401, which matches fail-closed behavior. Whether the production variable is set, and to a value of at least 32 characters, is `NEEDS_RUNTIME_VERIFICATION`. No token was sent.

### R-10 — dependency audit

Severity: low.

Commands:

```text
pip-audit -r requirements.txt --progress-spinner off
```

`pip-audit` 2.10.1 resolved `requirements.txt` in a disposable virtualenv (Django 5.2.18 and the other pinned or ranged requirements). Output: `No known vulnerabilities found`. Exit 0. A second run with `--no-deps` on the requirement file alone also reported no known vulnerabilities.

`requirements.txt` uses ranges for Django, django-otp-webauthn, djangorestframework, sqlparse, and urllib3, and leaves django-environ, psycopg2-binary, whitenoise, gunicorn, django-bootstrap3, requests, drf-spectacular, pytest, and pytest-django unpinned. Hashes are not recorded.

Proposed fix: pin a lockfile with hashes in a later change. This audit adds no runtime dependency.

## Read-only probe

`scripts/security/check_exposure.py` prints method, URL, status, byte count, and result. It never prints a body. Timeout and connection errors are `UNVERIFIED` with no exception text. HTTP 5xx is `UNVERIFIED`. HTTP 404 is `PASS`. HTTP 200 is `EXPOSURE`. Other completed statuses, including 302, are `OBSERVED`. Redirects are not followed. Each URL is requested once.

Tests in `tests/test_check_exposure.py` mock the HTTP client. They do not contact production.
